# DP-5: composite in the web app: pack selection, two PayPal approvals with progress, per-item lines

Task: let a buyer choose a two-publisher pack, approve once in UnitMarket, approve at PayPal once per publisher with "Step 2 of 2", and see one line per item from stored data; wire the engine and the seeding in composition.
Package: `apps/web` (including `composition.server.ts` and `src/server/dryrun-model.ts`) Owner: Sonnet 5.5 builder, effort high (holds composition) Reviewer: Opus 5.5 high (routes and composition), screenshot review for copy; Sakthi merges
Wave: MVP-D W4, after DP-3 and DP-4 merge. Decisions: D-041 (owner, decided), OQ-8 (owner, open: wording), OQ-5 and OQ-17 (table A). Requirements: D-01 to D-03 and D-07 (user-visible side), P6, P13, P16, A11Y-4, A11Y-7, COMP-4, PAY-10.

Goal. **Pack (OQ-17):** `/discover` results get a checkbox per item and a "Buy selected together" button. The server decides; the page only explains `mixed_currency` and `too_many_publishers` in plain words. It posts the existing `proposal` selection with several `offer_ids`. **Approve:** `/approve/[id]` shows one block per publisher (display name, items, subtotal), the total, and, when `snapshot.settlement` is present, "You will approve 2 payments at PayPal, one for each publisher. You are charged only after you have approved both." **Checkout:** `POST /api/orders/[ref]/checkout` returns `{ approve_url, progress }`. **Between approvals (OQ-5):** `/checkout/return` calls `onBuyerReturn`. While a provider order still awaits the buyer, it renders "Step 2 of 2: approve your payment to <publisher> at PayPal" with one button to that stored approve URL (no automatic redirect) and "If you do not approve within <N> minutes, the whole order is cancelled and nothing is charged.", where N is derived from `pack_approval_window_ms` (rounded down to whole minutes), never typed in; the golden pins the default 60 and one test runs with a 30 minute window (L-8). It never uses an id from the URL. **Cancel:** a static `/checkout/cancel` page (PayPal's cancel URL already points there): "You did not approve this payment at PayPal. Nothing was charged. If you approved another payment of this order, it will not be taken unless you approve the rest." No cancel API (cut). **Dry run:** `/checkout/dry-run/[order]` shows one approve step per provider order with its own scenario selector, so `happy` then `declined` gives a partial offline. The model refuses a reused `invoice_id` for one payee with `DUPLICATE_INVOICE_ID`, as the owner's account does (D-033). **Order page:** one line per item: "Ready in your library", "Not charged: PayPal declined this payment" (declined, failed or abandoned only), "On hold while we check it" (frozen, H1), "Confirming payment", in an `aria-live="polite"` region. Library and receipt keep their pages and show the DP-4 line outcome. **Composition:** binds the new engine views; sets `pack_approval_window_ms` explicitly; applies `seedSupplement` (DP-1) on every boot. Offline, every publisher gets a distinct fake payee as today. In sandbox mode (D-041), boot runs one transaction (M-3). First, `harbour-ledger` gets `payee_shared = true` where its stored id equals the owner's id; this sets the flag only and never rewrites the id. On the MVP-C disk Harbour already stores the owner's id without the flag. Then `quayside-gazette` gets the owner's id, `payee_verified_at` and `payee_shared = true` where its id is null. Each change writes one `audit_log` row. If Harbour stores an id that differs from the owner's, boot sets nothing and logs one refusal line, with no partial write, so `publishers_merchant_unshared` can never fail at boot. The `/ops` page states from that data "Both publishers are paid into the owner's sandbox account (…<last 4>)". Labels come from `environment`.

Inputs: DP-1 to DP-4 engine functions and views, `apps/web/src/**`, `apps/web/e2e/support.ts`, `scripts/route-inventory.mjs`, CO-8 copy rules.

Outputs: the DP-5 files in `mvp-d-overview.md` section 4. Also `apps/web/src/app/api/approvals/route.ts`: add `too_many_publishers: 422` to `STATUS` and a plain `TEXT` line. Seeding: `seedSupplement` runs only after the base-seed check (`composition.server.ts:553` seeds the base only when there are no publishers), so the supplement is never the first seed on an empty disk. The two `payee_shared` flag updates stay two statements in one transaction, Harbour first.

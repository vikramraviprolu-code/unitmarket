# BU-9 (hotfix): a stale checkout whose PayPal order is gone must be closed, and an idle pass must not spin

Task: stop the endless `get_order` polling seen in the owner's sandbox run on 26 Oct (about 115 calls in 100 s, nearly all HTTP 404, against the 300-call day of D-035).
Package: `domain/payments` (`due.ts`), `packages/jobs` (`loop.ts`) Owner: Sonnet 5.5 builder, effort high (money path, PayPal call budget) Reviewer: Opus 5.5 high; Sakthi merges
Cause: `abandonOne` reads an `awaiting_buyer` order older than `abandoned_checkout_ms` and returns `skipped` for any answer but an order. A PayPal order that no longer exists answers 404 = `not_found`, which is neither blocked nor transient, so the order stays `awaiting_buyer` for ever; `nextDueAt` keeps reporting it overdue, the loop wakes after `MIN_SLEEP_MS` (100 ms) on every pass, and each pass reads it again (held back only by `min_call_gap_ms`).

Goal: (1) When `getOrder` answers `not_found` for a single-route order, PayPal has no such order, so nothing can be captured: abandon it through the existing abandon step (order `abandoned` through `endWholeOrder`, which derives the status with `refreshOrder`; units declined; `prepared` operations failed), then it is never read again. Not when a capture operation of the order is `sent` or `unknown` (the answer may have been lost: keep the order, `skipped`, the reconciler owns it), and not when any unit has a capture id or a verified capture, or the PayPal order row is in a state that says a capture was aimed at it (`capture_requested`, `capture_claimed`, `unresolved`, `captured`) or is already terminal. Both are re-checked under the order lock, in the abandoning transaction. A log line `payments.due.abandoned_not_found` (order_ref only) is written; no ops alert (no existing kind fits; no new kind). A pack (more than one PayPal order, or route `per_publisher`) is NOT changed: one `not_found` PayPal order says nothing about the others, which this pass does not read, so it stays `skipped` as before; DP-2b ports the due pass for packs. (2) `startLoop`: a pass whose counts are all zero does not wake again after `MIN_SLEEP_MS` because `nextDueAt` is overdue; it sleeps `max_sleep_ms`. A zero pass with `nextDueAt` in the future still wakes at that time; a pass with progress behaves as before. Two existing loop tests used an all-zero stand-in pass to pin the 100 ms floor; they now return one processed item, which is the case that floor is for. This guards every unreadable or blocked item against the same spin.

Inputs: `domain/payments/src/{due,composite,store,apply}.ts`, `packages/jobs/src/{loop,budget}.ts`, `packages/contracts/src/paypal.ts` (`not_found`).
Outputs: `domain/payments/src/due.ts`, `packages/jobs/src/loop.ts`, tests `domain/payments/src/due.notfound.state.test.ts`, `packages/jobs/src/loop.idle.integration.test.ts`, `tests/mvp-a/stale-not-found.integration.test.ts` (the only package that reaches both the real loop and a real payments world through public entry points; its `package.json` and `pnpm-lock.yaml` gain one workspace link, `@umsbx/jobs`, no external package), this spec.

# DP-2: provider orders for route D2: create, approve "1 of 2", capture and read-back per PayPal order

Task: settle a `per_publisher` order as one PayPal order per publisher, each with its own state, keys, invoice id, approval, capture and matching read-back, and derive the order status (including `paid_partial`) from them.
Package: `domain/payments`, `packages/db` (migration 0011), `packages/contracts` (paypal), `packages/paypal` (`build-create.ts`) Owner: Sonnet 5.5 builder, effort high ($) Reviewer: Opus 5.5 high, diff review plus mutation checks; Sakthi merges
Wave: MVP-D W2, after DP-1. Prerequisites: OQ-3, OQ-4, OQ-6, OQ-9, OQ-14. Requirements: D-01, D-02, D-05, P3, P4, P5 per unit, P6, P14, P17, D-014/D-018, D-020, architecture 4.1, 4.2, 5.

Goal. Migration `0011_provider_order_state.sql`: `provider_orders` gains `position int NOT NULL` (UNIQUE with `order_id`), `po_ref ums_id NOT NULL UNIQUE`, `publisher_id` (NULL only for `single`, UNIQUE with `order_id`), `state` (CHECK in the overview's eleven states); `operations` gains `provider_order_ref` (FK). Existing rows backfill: `position` 1, `po_ref` = the order's `order_ref`, `state` from the order status, every operation pointing at its order's one provider order. **Place:** a snapshot with `settlement.route = 'per_publisher'` writes one provider order per publisher (positions by `publisher_id`, `po_ref = <order_ref>-p<n>`, state `prepared`), each unit pointing at its own provider order, and one `create` operation per provider order keyed `umsC-<po_ref>`; `single` keeps today's rows and keys exactly. **Create (OQ-3 eager):** `beginCheckout` sends every prepared create, one at a time, outside any transaction, each request with one unit, `custom_id` = `order_ref`, `invoice_id` = `po_ref` (new optional `invoice_id` in `CreateOrderReqSchema`, allowed only with one unit; `buildCreateBody` uses it), payee per D-028. It returns the first `awaiting_buyer` approve URL and `progress { step, of }` only when every provider order is created; a rejected create fails the whole order, nothing charged; an unknown create leaves the order `created` for the reconciler. **Return (OQ-4):** the return URL is a trigger only; the handler reads every `awaiting_buyer` provider order by its stored id (P6, never `token` from the URL); APPROVED and matching moves it to `approved`; while any is still awaiting, the answer is the next approve URL and `step` of `of`, and no capture is sent. When all are `approved`: one readiness check over every item; any failure fails the whole order before any capture (OQ-14, not charged); then each provider order, in position order, is re-read and captured through the one compare-and-set path on its own capture operation (`umsK-<po_ref>`, D-014 key cap per provider order), then read back (order GET plus capture GET) against its slice of the expected transaction (`expectedFor(expected, units of that provider order)`; claims of every unit of the order are passed so a capture id reused across provider orders is `capture_id_reused`). **Freeze (OQ-14):** before any capture, any mismatch freezes the whole order and nothing is captured; after a capture, a unit mismatch freezes that provider order only (`frozen`, `frozen_order` alert with its unit), the others continue. **Status:** a pure `deriveOrderStatus(states, current)` in `composite.ts` gives the order status (overview section 3); entering `paid_partial` raises one `partial_composite` alert (reason `partial`). **Other paths:** `cancelCheckout(d, { order_id, actor })` (buyer, new) abandons every provider order while none is `capture_requested` or later, else `wrong_state`; the 24 h sweep (OQ-6) captures only when every provider order reads APPROVED and matches, else abandons all, nothing charged; reconcile, the paid re-read, startup recovery and webhooks work per provider order (a webhook makes only its provider order's read-back due); INV5 holds per provider order. `OrderView` gains `progress`, `provider_orders [{ position, publisher_id, state }]` and per-item `publisher_id`.

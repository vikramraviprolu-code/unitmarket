# MVP-D: two publishers in one approval (composite), lane overview

Status: proposal, revision 2 (after the Opus review of 0e3730a), 2026-10-25, written by the design-spec writer (Opus 5.5). No product code changes here. Route: **D2** (decision-log D-007, architecture decision D-3): one PayPal order per publisher under one UnitMarket approval. D1 and D3 are not assumed: spike W11 (runbook step 16) has not run and needs a second sandbox Business account that does not exist. No commission. This is the **minimum viable MVP-D** of the review; cut items are in section 5. "Passing offline" proves the modelled cases only, not PayPal compatibility.

## 1. Facts established from the code

What already supports N units or N provider orders:

- **Schema.** `packages/db/migrations/common/0004_money.sql`: `orders.status` already allows `paid_partial`; `provider_orders` exists with `route IN ('single', 'per_publisher')` and the comment "One internal order maps to 1..N PayPal orders"; `order_units.provider_order_ref` points a unit at its provider order; `order_units.publisher_id` and `payee_merchant_id` are per unit; `ledger_entries` are per unit and capture; `receipts` are per order and versioned; `approvals` are checked to expire 15 minutes after creation (line 19).
- **Approval.** `domain/approval/src/approval.ts` `requestApproval` builds one snapshot over up to 5 offers (`MAX_ITEMS`, selection kind `proposal`), groups items into per-publisher blocks with their own `payee_merchant_id` and `amount_minor`, refuses `mixed_currency` and a second corridor before approval, and refuses `publisher_unverified` when a publisher has no `paypal_merchant_id` or no `payee_verified_at` (P18, D-04 already enforced). `placeOrder` re-checks every publisher's payee and answers `payee_unavailable` (409) (`domain/payments/src/place.ts`).
- **Order and units.** `placeOrder` writes one unit per publisher, entitlements per item, and an expected transaction with one expected unit per publisher.
- **Match and apply.** `matchReadback` (`match.ts`) checks per unit (payee, amount, capture amount, capture id reuse across units). `applyReadback` (`apply.ts`) already derives `paid` / `paid_partial` / `failed` from unit terminal states.
- **Recovery.** `CaseKind` `partial_composite` exists (`packages/contracts/src/recovery.ts`), in `ALERT_CASE_KINDS`, with a 24 h SLA and a buyer message; a case opens when an alert of that kind exists (`applyAutomaticRules`). Buyers may already report `refund_requested` (`rules.ts` `BUYER_KINDS`, 48 h SLA) operators already have `offer_refund` (which only requests; nothing executes it, ASSUMPTIONS open item) and the MFA refund route `POST /api/refunds` (CO-8, requests and executes).
- **Ledger and refunds.** Ledger rows, INV1, refunds and the ledger guard trigger are per unit; one refund lookup already picks the unit's own provider order (`refunds.ts` ~395).
- **PayPal adapter.** `buildCreateBody` builds N purchase units and leaves the payee out only when it equals `UMS_OWN_MERCHANT_ID` (D-028, `build-create.ts:91`). The dry-run model (`apps/web/src/server/dryrun-model.ts`) keeps many PayPal orders, each with its own approval scenario.
- **Transport and gate.** `mvp_c_refunds` allows a `purchase_units[].payee`; `mvp_b_polling` refuses one only when a payee is in the body (`sandbox.ts`), so a body whose payee was left out under D-028 passes either scope. The amount cap is checked per call (`packages/safety/src/gate.ts:77`), that is per PayPal order. `PayPal-Mock-Response` is not on the header allow-list (`sandbox.ts:126-132`). On the host `UMS_OUTBOUND_SCOPE` is pinned to `mvp_c_refunds` (`scripts/check-hosting.mjs:74`).

What does not exist, or contradicts D2:

1. **The engine reads one provider order and one operation per kind per order.** `beginCheckout` uses `providers[0]` and builds one create from all units (`checkout.ts`); `applyReadback` throws unless exactly one provider order exists (`apply.ts` ~108); `onBuyerReturn` reads `[0]` and acts only while the order is `awaiting_buyer` (`return.ts:45-55`); the paid re-read is `readAndApply` (`reconcile.ts:46`, `[0]`); `expireCreate` (`due.ts:502`), the capture retry (`due.ts:351`, `:375-399`, `:407`), the abandoned-checkout sweep `abandonOne` (`due.ts:556-560`, `:582`, `LIMIT 1`) and two refund reads (`refunds.ts` ~796, ~1122) are per order; `loadOperation` is `order_id, kind ... LIMIT 1` (`store.ts:202`); the capture key and the capture operation come from `order_ref` and `(order, kind)` (`capture.ts:57, 66, 77, 108, 136`); `webhooks.ts:279` targets the order's one read-back; startup recovery's `IN_FLIGHT` and `UNPOLLED_ORDERS` key on the order status (`recover.ts`); `UPDATE provider_orders ... WHERE order_id = $1` in `capture.ts` and `reconcile.ts`; the test worlds read the first provider order (`domain/payments/src/support.ts:619, 642`, `ops/support.ts`). `operations` has no provider-order column.
2. **`lockOrderRows` does not lock `provider_orders`** (`store.ts:161-168`) although D-020 and the READINESS lock order name them with orders.
3. **A two-publisher approval today produces a D1-shaped order** (one `single` PayPal order with two payees). In sandbox mode only `harbour-ledger` gets a merchant id (`composition.server.ts:575-582`), so a second publisher is refused `publisher_unverified` at approval first; with two payees in the body `mvp_b_polling` would refuse and `mvp_c_refunds` would send.
4. **Duplicate invoice ids.** For a one-unit order `invoice_id` is `order_ref` (`build-create.ts invoiceIdFor`): two D2 orders of one UnitMarket order would share it, and duplicate-invoice blocking is on for the owner's account (D-033).
5. **One merchant id per publisher row.** `publishers.paypal_merchant_id` is `UNIQUE` (`0001_core.sql`, constraint `publishers_paypal_merchant_id_key`).
6. **No second USD publisher.** The seed has `harbour-ledger` (US, USD) and `northfield-quarterly` (GB, GBP; corridor disabled). `seedCatalogue` runs only when no publisher exists (`composition.server.ts:552-553`), so new seed rows never reach the persistent MVP-C disk; `seededIds` uses one counter per seed (`packages/runtime/src/seeded-ids.ts:8-10`), so a new publisher inside `SEED_DATA` would shift every later id in seeded test worlds (`packages/testkit/src/catalogue.ts:11`, `tests/mvp-a`).
7. **Unit mismatch freezes the whole order** (FIX-05A, `apply.ts` ~262); D-05 asks for a freeze of that unit after capture. A mismatch read returns before `issueReceiptIfChanged` (`apply.ts:145-170`).
8. **Nothing raises `partial_composite`**; no per-publisher ledger sum or invariant (P11 per publisher); receipt lines do not say "not charged".
9. **Web.** The discover page selects one offer; no progress across two PayPal approvals; `cancel_url` points to `/checkout/cancel`, which has no page.

## 3. Shared names (every lane uses these)

- Route values: `single` (one publisher; unchanged rows, keys and hash) and `per_publisher` (D2). Only a snapshot with 2 publishers carries `settlement: { route: 'per_publisher', payments: 2 }`.
- Provider order columns (0011): `position` (1..N by `publisher_id`), `po_ref` (`<order_ref>-p<position>`; for `single` it equals `order_ref`), `publisher_id`, `state`, `first_approved_at`.
- Provider order states: `prepared`, `awaiting_buyer`, `approved`, `capture_requested`, `capture_claimed`, `unresolved`, `captured`, `declined`, `frozen`, `failed`, `abandoned`. Terminal: `captured`, `declined`, `frozen`, `failed`, `abandoned`. **Not charged** means `declined`, `failed` or `abandoned` only; `frozen` means on hold (money may have moved).
- Order statuses: unchanged enum. `paid_partial` = every provider order terminal, at least one `captured`, at least one not. `mismatch = true` whenever any provider order is `frozen`.
- Keys: `umsC-<po_ref>`, `umsK-<po_ref>[-n]` (D-014 cap per provider order), read-back row `umsB-<po_ref>`; `custom_id` = `order_ref`; `invoice_id` = `po_ref`. N single-unit creates; no new operation, header, scope or seal change; approval row shape unchanged.
- Alerts: `partial_composite` (reason `partial`, one per order) only when a provider order is not charged; `frozen_order` for a held one.
- Config: `pack_approval_window_ms` (default 3 600 000) from the first approval at PayPal.
- Test payee ids: `SBXPAYEEHARBOUR1`, `SBXPAYEEQUAYSIDE2` (distinct, fake); the sandbox mapping is stated per run (OQ-1).

## 5. Later, only if time (cut from the minimum viable MVP-D)

Buyer `cancelCheckout` API (the 24 h sweep and the pack window cover abandonment; the static cancel page says nothing was charged); `chooseCompositeOutcome`, its route, the case choice buttons and the 7-day auto-close (keep is the default by doing nothing; a refund goes through `refund_requested` and the operator's MFA refund route, CO-8); `publisherReport` and the ops page section; a full per-publisher receipt section; "Bought together with" in the library; a second sandbox merchant (OQ-1 A).

## 6. Safety rules that do not move

Five locks; two-key approval; the approval row's scope, operations and per-call amount cap cover every PayPal order of a pack (the pack total is not checked by the gate and is bounded only by 2 x the cap); one capture per PayPal order (P4) through the one compare-and-set path; access only after a verified capture and a separate matching read-back including the payee, per provider order; D-020 lock order (orders, then provider_orders by position, operations, order_units, refund_requests, recovery_cases, entitlements, ledger and receipts); append-only ledger; a webhook only makes a read-back due; the 15 minute approval is consumed once by `placeOrder` and covers every provider order of that order; no automatic substitution; no Payouts, no platform fee, no Partner Referrals. Migrations are forward-only.

## 1. Facts established from the code

What already supports N units or N provider orders:

- **Schema.** `packages/db/migrations/common/0004_money.sql`: `orders.status` already allows `paid_partial`; `provider_orders` exists with `route IN ('single', 'per_publisher')` and a comment "One internal order maps to 1..N PayPal orders"; `order_units.provider_order_ref` points a unit at its provider order; `order_units.publisher_id` and `payee_merchant_id` are per unit; `ledger_entries` are per unit and capture; `receipts` are per order and versioned.
- **Approval.** `domain/approval/src/approval.ts` `requestApproval` builds one snapshot over up to 5 offers (`MAX_ITEMS`, selection kind `proposal`), groups items into per-publisher blocks with their own `payee_merchant_id` and `amount_minor`, refuses `mixed_currency` and a second corridor before approval, and refuses `publisher_unverified` when a publisher has no `paypal_merchant_id` or no `payee_verified_at` (P18, D-04 already enforced for one and for many publishers). `placeOrder` re-checks every publisher's payee and answers `payee_unavailable` (409) (`domain/payments/src/place.ts`).
- **Order and units.** `placeOrder` writes one unit per publisher, entitlements per item, and an expected transaction with one expected unit per publisher.
- **Match and apply.** `matchReadback` (`match.ts`) checks per unit (payee, amount, capture amount, capture id reuse across units). `applyReadback` (`apply.ts`) already derives `paid` / `paid_partial` / `failed` from unit terminal states, and existing tests cover a two-unit `paid_partial` (`apply.state.test.ts` "one unit matched, the other declined").
- **Recovery.** `CaseKind` `partial_composite` exists in `packages/contracts/src/recovery.ts`, in `ALERT_CASE_KINDS`, with an SLA (24 h) and a buyer message (`domain/recovery/src/{rules,messages}.ts`); a case opens when an alert of that kind exists (`applyAutomaticRules`).
- **Ledger and refunds.** Ledger rows, INV1, refunds and the ledger guard trigger are per unit; `refunds.ts` already picks the unit's own provider order in one lookup (`p.id IS NOT DISTINCT FROM u.provider_order_ref`).
- **PayPal adapter.** `buildCreateBody` builds N purchase units and omits the payee only when it equals `UMS_OWN_MERCHANT_ID` (D-028, `packages/paypal/src/build-create.ts`); the dry-run order model (`apps/web/src/server/dryrun-model.ts`) keeps many PayPal orders, each with its own approval scenario.
- **Transport.** `mvp_c_refunds` already allows `purchase_units[].payee`; `mvp_b_polling` refuses it (`packages/transport/src/sandbox.ts`). The outbound amount cap is checked per create call, that is per PayPal order.

What does not exist, or contradicts D2:

1. **The engine is single-provider-order everywhere.** `beginCheckout` uses `providers[0]` and builds one create request from all units (`checkout.ts`); `applyReadback` throws unless exactly one provider order exists (`apply.ts` line ~108); `onBuyerReturn`, `reconcileOrder`, the paid-order re-read (`due.ts` ~580) and two refund read paths (`refunds.ts` ~796, ~1122) read `ORDER BY id LIMIT 1`; `loadOperation(order, kind)` returns one operation per order and kind (`store.ts`); `UPDATE provider_orders ... WHERE order_id = $1` in `capture.ts` and `reconcile.ts`. `operations` has no provider-order column.
2. **A two-publisher approval today produces a D1-shaped order.** `placeOrder` writes one `single` provider order holding both units with different payees. In sandbox `mvp_b_polling` refuses the payee (fails closed); under `mvp_c_refunds` it would be sent. This is the route we must not assume.
3. **Duplicate invoice ids.** `invoice_id` is `order_ref` when an order has one unit (`build-create.ts invoiceIdFor`). Two D2 orders of one UnitMarket order would carry the same `invoice_id`; PayPal's duplicate-invoice blocking is on for the owner's account (D-033), so the second capture to the same merchant would fail `DUPLICATE_INVOICE_ID`, which the engine maps to a frozen order.
4. **One merchant id per publisher row.** `publishers.paypal_merchant_id` is `UNIQUE` (`0001_core.sql`). Both publishers cannot both be paid into the owner's single sandbox account (D-028) without a schema change (OQ-1).
5. **No second USD publisher.** The seed (`domain/catalogue/src/seed-data.ts`) has `harbour-ledger` (US, USD) and `northfield-quarterly` (GB, GBP; corridor `gb-gbp` disabled). Today every two-publisher pack is mixed currency.
6. **Unit mismatch freezes the whole order** (FIX-05A, `apply.ts` `stuck` branch). D-05 asks for a per-unit freeze after capture.
7. **No `partial_composite` alert is ever raised** by payments; recovery only reacts to one. Buyer choices (keep or refund) do not exist; `offer_refund` is operator-only.
8. **No per-publisher ledger sum, invariant or report** (P11 per publisher); receipts list items, not publishers.
9. **Web.** Approve and discover pages select one offer; no progress across two PayPal approvals; `cancel_url` points to `/checkout/cancel`, which has no page; the order view carries one `approve_url`; the sandbox seeding in `composition.server.ts` pays only `MVPB_PUBLISHER_SLUG`.

## 3. Shared names (every lane uses these)

- Route values: `single` (one publisher; unchanged behaviour) and `per_publisher` (D2). A snapshot with 2 publishers always carries `settlement.route = 'per_publisher'`.
- Provider order columns (migration 0011, DP-2): `position` (1..N, by `publisher_id` order), `po_ref` (`<order_ref>-p<position>`; for `single` it equals `order_ref`, so existing keys do not change), `publisher_id`, `state`.
- Provider order states: `prepared`, `awaiting_buyer`, `approved`, `capture_requested`, `capture_claimed`, `unresolved`, `captured`, `declined`, `frozen`, `failed`, `abandoned`. Terminal: `captured`, `declined`, `frozen`, `failed`, `abandoned`.
- Order statuses: unchanged enum. `paid_partial` = every provider order terminal, at least one `captured`, at least one not. `mismatch = true` when any provider order is `frozen`.
- Keys: `umsC-<po_ref>`, `umsK-<po_ref>[-n]`, read-back row `umsB-<po_ref>`; `custom_id` = `order_ref` on every PayPal order; `invoice_id` = `po_ref`.
- Alert: `partial_composite` (reason `partial`, one per order). Case choices: `keep` (default) and `refund_captured`.
- Test payee ids: `SBXPAYEEHARBOUR1`, `SBXPAYEEQUAYSIDE2` (distinct, fake); sandbox mapping is stated per run (OQ-1).

## 5. Safety rules that do not move

Five locks; two-key approval; the approval row's scope, operations and per-call amount cap cover every PayPal order of a composite; one capture per PayPal order (P4) through the one compare-and-set path; access only after a verified capture and a separate matching read-back including the payee, per provider order; D-020 lock order (orders and provider_orders, operations, order_units, refund_requests, recovery_cases, entitlements, ledger and receipts); append-only ledger; a webhook only makes a read-back due; the 15 minute approval snapshot is consumed once by `placeOrder` and covers every provider order of that order; no automatic substitution; no Payouts, no platform fee, no Partner Referrals.

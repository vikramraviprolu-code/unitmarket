# Spec: landing page, buyer accounts, role sign-in pages (ID-ACCOUNTS)

Task: a good landing page with three doors (Buyer, Seller, Operator); any buyer can create an account (username and password) and come back; sellers and operators get their own clear entry pages; access management follows current good practice.
Package: `packages/security`, `packages/db` (migration 0016), `apps/web` (pages, routes, composition) Owner: builder (Sonnet) Reviewer: Opus (security review)
Branch: `feat/id-accounts-landing` Commit: `feat(web): <what> (ID-ACCOUNTS)` Decisions: owner brief 31 Oct (landing with three buttons; buyers self-register with logon and password; sellers apply and the owners handle them by hand; operators keep the full authentication).

Goal: `/` shows what UnitMarket is and three doors. A buyer reads what they need, creates an account in one form, signs in with it, and can return any day. A seller reads what to prepare and applies (existing Apply form). An operator reaches a sign-in page with passcode, name and authenticator code. The existing test persona sign-in (judges, testers, e2e) keeps working unchanged.

Pages (words in `lib/account-copy.ts`, a golden test pins them; styles in a new `app/auth.css`, tokens only, works in both skins):

- `/` landing: hero ("Buy just the article you need" stays), then three role cards: Buyer ("I want to read"), Seller ("I want to publish"), Operator ("I run the platform"), each one sentence, what you need, one big button. Under them the offer shelf as today. A signed-in actor sees their own door as "Go to my library / publisher pages / operations" and the other doors stay visible. Server-rendered, no script needed.
- `/buyer`: plain instructions. What you need: a display name, a username (3 to 30 letters, digits, dot, dash, underscore), a password of 12 or more characters (a phrase of four words is fine), your country. No email is asked and none is sent; a lost password is reset by the operator (contact address from the existing legal constant, `unitmarket@raviprolu.com`). Buttons: Create account, Sign in.
- `/signup`: form: display name 2 to 60, username, country (two capital letters, same as Apply), password and repeat, a required checkbox "I accept the Terms and the Privacy notice" (links), hidden honeypot. Show the rules next to the field, a show/hide control, paste allowed, `autocomplete="new-password"`. On success the buyer is signed in and goes to `next` (safe path) or `/discover`.
- `/signin/buyer`: username, password (`autocomplete="current-password"`, show/hide), link "Forgot your password?" to `/help/password` (what to do, contact address) and to Create account. One failure message for every refusal: "That username or password did not work."
- `/seller`: instructions: what to prepare (publisher name, country, a website or public profile for the note, later a PayPal business account for payouts, the Publisher terms). Buttons: Apply to publish (`/apply`), Check an application (`/apply/status`), Sign in (`/signin/seller`). One honest paragraph: applications appear in Operations, the owners review them and reply by hand; no email is sent by the app in this demo.
- `/signin/seller`: choose your publisher (the existing persona list) and passcode; says that publisher sign-in is set up by the owners after an application is approved. Posts to the existing `/api/session`.
- `/signin/operator`: operator name, passcode, authenticator code, with the hint text already in `SignInForm` (what leaving the code empty allows). Posts to the existing `/api/session` with persona `operator`.
- `/signin` (existing): keep the persona form untouched under a heading "Judges and testers", and add the three role cards above it. Existing e2e and tests keep passing unchanged.
- `/account` (buyer only): change password (current, new, repeat) and "Sign out on all devices". Header nav for a buyer gains "Account" (`lib/nav.ts`; update its test).
- `/help/password`: lost password steps (no email in the demo: contact the operator, who resets it at the terminal).

Backend:

- Migration `packages/db/migrations/common/0016_buyer_accounts.sql`: table `buyer_accounts` (buyer_id PK references buyers, username unique with a CHECK on the shape, password_hash, failed_attempts int, locked_until timestamptz null, password_changed_at, created_at, updated_at). System-only: no buyer or publisher policy. Update the migration pin tests the way 0012 to 0015 did.
- `packages/security/src/accounts.ts` (uses `deps.db`, `deps.ids`, `deps.clock`, `deps.audit`; no new dependency): `createAccount`, `verifyAccountLogin`, `changePassword`, `resetPasswordForOperator`, `checkPasswordPolicy`. Hash with the existing scrypt code in `passcode.ts` (salt from `deps.ids`). `buyers.auth_subject = 'account:<username>'`; the buyer id comes from `deps.ids`. A `consents` row for the Terms and Privacy at signup (look at how the existing consent flow writes it and reuse it).
- Password policy (NIST 800-63B): 12 to 128 characters after NFKC, no composition rules, refuse a list of the 200 most common passwords (file in the package, text only), refuse a password that contains the username or equals the display name, never trim or truncate, never log.
- Login: unknown username and wrong password cost the same (verify against a fixed dummy hash for an unknown name) and return the same body and status. Per account: 20 consecutive failures lock the account 15 minutes, doubling to a cap of 1 hour (high on purpose, NIST 800-63B allows up to 100: the real throttle is the per IP and username limit below, so a stranger at one address cannot keep a known name locked); a failure count whose last failure is older than 24 hours is forgotten; a right password resets the count; a locked account answers like a wrong password (no "locked" word, `Retry-After` only on the 429 from the rate limit). Per IP and username: 5 per 15 minutes (same bucket style as `/api/session`).
- Signup: 5 per hour per hashed address (`ip_known` gating exactly like `/api/applications`: unknown address answers busy and spends nothing); a taken username answers 409 "That username is taken." (the only place a name's existence shows; rate limited); honeypot answers the normal success and stores nothing.
- Session: a new session on every login and signup (rotate), the old session of that browser is revoked if its cookie is present, cookie flags unchanged (`__Host-`, HttpOnly, Secure, SameSite=Lax), 8 hours absolute and 30 minutes idle unchanged. Change password revokes every other session of that buyer and keeps the current one. Sign out unchanged.
- Routes (all `.strict()`, CSRF origin check, small body caps, generic errors, no internal id in any answer): `POST /api/accounts` (signup), `POST /api/accounts/login`, `POST /api/accounts/password` (buyer session), `POST /api/accounts/sessions/revoke-all` (buyer session). Add each to the route table and the maintenance walk.
- Audit rows (no password, no raw username for a failed login: hash it): `account.signup`, `account.login`, `account.login_failed`, `account.locked`, `account.password_changed`, `account.sessions_revoked`.
- Operator reset CLI `pnpm accounts:reset-password --username <name>` modelled on `safety:approve` (TTY only, refuses in CI, passes the env guard, prompts twice with echo off, applies the same password policy, revokes the account's sessions, one audit row). It is the "lost password" path.
- Operator sign-in stays as is (name, passcode, code, lockout). This task only gives it a clear page.

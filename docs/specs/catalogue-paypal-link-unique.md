Task: one verified PayPal address belongs to one publisher (POB-LINKU)
Package: domain/catalogue (plus one migration in packages/db and the operator copy in apps/web) Owner: Sonnet builder Reviewer: Opus, merge by the reviewer
Status: the rule is the coordinator's proposal. Owner confirmation is pending; the PR stays unmerged until it is given.

Goal: the address in `publisher_paypal_links` is where a publisher is paid (D-089 item 1: a publisher brings their own PayPal account). A verified payout destination must therefore belong to exactly one publisher. At most one `verified` link may exist per normalized address across all publishers. Normalized is what `normalizePaypalEmail` already stores (trimmed, lower case, one plain address); the index repeats it as `lower(btrim(paypal_email))`. Several `requested` links may share an address, because a request proves nothing. The publisher flow is unchanged: a publisher is never told that an address is verified for someone else (no existence leak). The refusal happens when the operator verifies, with the new operator only error `email_in_use`, mapped to 409 on the ops route and to operator copy. The same publisher may change an address and later verify it again. There is no `payee_shared` style exemption: demo publishers get distinct reserved `.invalid` addresses in another lane.
Why at verification: a duplicate does not by itself misdirect a payout (each payout reads its own publisher's verified link, `payout.ts`), but if an operator verified publisher B's request for publisher A's address, B would be paid into A's account. The control is the operator step, and the database enforces it as the last line.

What the docs say (searched docs/specs, docs/business-rules, docs/design, docs/decision-log.md for paypal_email, payee, D-041, D-089, OQ-1): no rule contradicts this. D-089 (1) says only that the publisher brings their own account and the app links it. `publisher_paypal_links` has publisher_id as its primary key and no rule on the address (`pob-p1-publisher-accounts.md`, migration 0028). The uniqueness rules found are about another column: `publishers.paypal_merchant_id` is UNIQUE unless both rows are `payee_shared` (D-041, OQ-1 option B, BR-FEE-4 and BR-FEE-5, `mvp-d-overview.md` 6). That is the demo's shared collection payee and does not touch the publisher's own payout address. No document allows or forbids two publishers sharing a payout address.

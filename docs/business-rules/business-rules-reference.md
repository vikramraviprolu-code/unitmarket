# UnitMarket business rules reference (4 Nov 2026)

Status: REFERENCE, first edition. Section 6 and the summary table were reconciled on 2026-11-07 with the code at
`660bb62b` (POB-M1, POB-P1, POB-G); the old wording is kept in the rows as History and in section 6a. Describes what the code does today, with a file and line for each rule. It changes
no behaviour. Where the code and an owner decision disagree, both are shown and the row is marked CONFLICT; the owners
decide which one wins. Nothing here is legal or tax advice.

Companion: `docs/business-rules/configurable-rules-design.md` (how these rules could become settings per seller,
buyer, category or agreement, and what the operator dashboard would show).

## 0. How to use this document

- **Purpose.** One place that says what UnitMarket's business rules are, where each one lives in the code, and who
  can change it today. Before a rule changes (for example "refunds within three weeks instead of one"), find it here,
  change it through the process in section 0.4, and update this file in the same PR.
- **Rule ids.** `BR-<area>-<n>`. Areas: REF refunds, DSP disputes and reversals, PRC price and currency, APR quote,
  approval and order, ACC access and delivery, FEE fees, settlement and payee, MAN agent mandates, PUB publishers,
  OPS operator powers and switches, EVT webhooks and events, AI discovery, PRV privacy, LIM rate limits, SIM
  simulation-only economics.
- **Status words.** ENFORCED: the code does it. DOC ONLY: an owner decision or design doc says it, the code does
  not. CONFLICT: code and decision disagree. OPEN: nobody has decided.
- **Who can change it today.** `code` (code change and deploy), `env` (an environment variable read by
  `packages/config`), `SQL` (a database edit, no screen), `op-screen` (an operator screen, usually with the
  authenticator code), `owner-CLI` (`pnpm safety:*` at the owner's terminal), `nobody` (a database CHECK or trigger:
  only a new migration changes it), `seller`, `buyer`.

### 0.2 What we found

1. **There was no business rules reference in either repository.** The nearest thing is Sivakumar's draft above. It
   was written against the simulation's article engine (USD, 20 percent share, view-only 48 h), was never confirmed,
   and predates the sandbox's direct-payee and five-day access design. This document supersedes it as the reference;
   section 9 maps its rule ids so nothing is lost.
2. **Rules live in five kinds of place**: code constants (most of them, including `DOMAIN_CONFIG` in
   `apps/web/composition.server.ts:1236-1258`), database CHECK constraints and triggers, seed rows
   (`corridors`, `access_policies`, `safety_switches`), environment variables (only a handful), and one operator
   screen per switch or decision. There is no settings table for commercial terms, and nothing varies per seller,
   buyer or category.
3. **Several owner decisions are not in the code yet**, chiefly D-089 (10 percent fee on top, payout after the
   refund window) and the 30-day retention rules in `docs/design/nfr.md`. See section 8.
4. **There is no buyer refund deadline in the sandbox.** An operator can refund a paid sale at any time. The
   simulation has a 7-day buyer request window. D-089 calls the 5-day access window "the refund window" but only for
   payout timing. The owners decided 7 days on 5 Nov (D-096, section 15).

### 0.4 How to change a rule (process until the design in the companion doc is built)

1. Find the rule here. Note every place it is defined (section 7 lists duplicates).
2. Record the owner's decision as a `D-nnn` row in `docs/decision-log.md`.
3. Change the code, constraint or seed through the normal spec and PR protocol (CLAUDE.md). A database CHECK needs a
   new migration; never edit an applied one.
4. Update this file in the same PR: value, file:line, status.
5. Say in the PR whether the change applies to past sales. Default: new sales only (see BR-APR-6 and the snapshot
   rule in the design doc).

## 15. Owner decisions on the open questions (D-096, 5 Nov 2026)

1. **Refund deadline.** 7 days by default, configurable per seller, buyer, category or agreement within 0 to 30 days.
   The access window is raised to at least the refund window, so default access becomes 7 days when this is built.
2. **Fee.** D-089 confirmed: 10 percent of the publisher price, added on top, paid by the buyer. BR-FEE-1 changed in
   the fee lane (POB-M1; reconciled below in section 6a).
3. **Who refunds.** Operator decides; a buyer may request within the deadline; an automatic approval below an amount
   is a tier B setting, off by default.
4. **PayPal fee on refund.** A setting (`refund.paypal_fee_bearer`), default seller, as today.
5. **Reserve.** None while payout waits for the refund window.
6. **Retroactivity.** New sales only; each sale freezes its terms.

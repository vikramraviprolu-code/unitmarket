## Payments second-pass fixes (FIX-PAY2)

Branch `fix/payments-pass2`. Decisions: D-018, D-019, D-020 in `docs/decision-log.md`. Findings: Opus second-pass review at main 7345ad4.

- **H-1 capture claim.** The claim transaction stores the read-back operation (`ensureReadbackOp`) together with `capture_claimed`. A process that dies between the claim and the post-capture read is finished by the poll. New invariant INV5: every order in `capture_requested`, `capture_claimed` or `unresolved` has an operation that is `sent` or `unknown` (or gave up with `failed`, `window_expired` after the 24 h window, which raised an alert).
- **H-2, M-1 refunds.** `refund_readback` (`umsRB-<request id>`) is created in the transaction that stores `pending`. Refund operations are looked up by their own request id, never per order. New invariant INV6: every open refund request (`sent`, `unknown`, `pending`) has an operation that is `sent` or `unknown`. A refund operation no longer switches off the 7 day re-read of a paid order.
- **M-2 `refunded_minor`.** Booking needs GET refund `COMPLETED` and the capture status `PARTIALLY_REFUNDED` or `REFUNDED`; the reported total is used only when it is above 0. `observeReadback` acts on the capture status first. A request that cannot be proven not refunded ends `unresolved` (reservation kept, alert), not `failed`. The test world reports `refunded_minor` 0 by default (`reportRefunded`). **Not done:** the refunded AMOUNT of a dashboard refund is not booked, because the PayPal port has no call that lists the refunds of a capture (`packages/paypal` and `packages/contracts` are outside this task). The unit ends `refunded` and access is revoked for a full refund; a partial dashboard refund raises `refund_unbooked` for a human. A change request for a `listRefunds(capture_id)` adapter method with fixtures is the next step.
- **M-3 lock order.** Documented below, applied to every money path, pinned by `lockorder.state.test.ts` (a spy on the SqlExecutor asserts the order of the locks of each transaction). `withSerializationRetry` (`packages/db/src/retry.ts`) retries 40P01 and 40001 up to 3 times; it is in the path of the PGlite driver and will be for the pg adapter.
- **LOW.** Startup recovery skips operations whose lease is still running and runs once per process (`startLoop` option `recover_on_start`, composition passes `false`); `nextDueAt` wakes the loop when a `sent` lease runs out. Capture re-send refusals close the capture as failed (D-018). The D-014 cap counts keys. Event ordering uses `seq` (INV4, recovery cases). `GET /checkout/return` starts the capture only for a page navigation (`Sec-Fetch-Dest: document`, `Sec-Fetch-Mode: navigate`); anything else gets a confirm button. A cross-site top-level navigation (which is also how PayPal returns the buyer) cannot be told from a hostile link by headers; it is harmless because the return only captures an order the buyer already approved at PayPal and the order reference is not guessable. The confirm button is a GET form (a page navigation), because server actions are barred by `check:routes`; a client that sends no Sec-Fetch headers at all cannot pass. `observeReadback` and `suspectReversal` lock the unit row before changing it.

### Lock order

Every transaction that moves money takes its row locks in this order, and a statement on a class already locked in the same transaction takes nothing new:

1. `orders` (and `provider_orders`), then every `operations` row of that order (`lockOrderRows` in `domain/payments/src/store.ts`);
2. `order_units`;
3. `refund_requests`;
   3a. `recovery_cases` (CO-4): a case is locked (`FOR UPDATE` or a compare-and-set `UPDATE`) after any order, unit or refund request it needs and before its entitlement. Opening a case locks the order or the entitlement first and then only INSERTs the case row (a new row nobody can hold; not a lock event). Settling a `refund_pending` case locks only the case and reads `refund_requests` without locks;
4. `entitlements` (with `access_windows`, `access_events`, `access_links`): a refund booking locks the unit's entitlements before it appends to the ledger, even for a partial refund (`bookEntry`, CO-4);
5. `ledger_entries`, `receipts`.

Pinned by `lockorder.state.test.ts` (rank 4.5) and the recovery and `refunds.complete` lock-order spies. Alerts, audit and provider-call rows are leaf inserts and are not part of the order. PGlite serialises all statements, so a deadlock cannot be reproduced here. **Real-Postgres race tests (concurrent capture/poll/refund/sweeper on one order, with the pg adapter) are required before MVP-C.**

## Gate conditions (FIX-GATE2, branch fix/gate-conditions)

Closes the conditions of the Opus gate review of main 364af49. Report: `docs/evidence/mvp-a-gate-2026-10-22-final.md`.

- **Condition: set `UMS_TRUSTED_PROXIES` before any hosted demo.** The count of reverse proxies in front of the app (integer 0 to 3, default 0, `packages/config`). With N above 0 the client address is the Nth entry from the right of `X-Forwarded-For`. With 0 and no socket address (Next.js route handlers receive none) all clients share one `no-address` limiter bucket: since FIX-GATE2 an exhausted shared bucket refuses only wrong passcodes, and the right passcode still signs in and resets that persona's bucket. That removes the lockout but also means brute force is bounded by the scrypt cost and the passcode strength only, so a hosted demo must set the count (and use a strong passcode) to get a per-client limit. A named address keeps the strict lockout.
- **Dry-run kill switch (M1).** The dry-run transport reads `paypal_outbound` first and answers `blocked kill_switch` (checkout and return answer `payments_paused`). Offline boots seed `paypal_outbound` ON (`changed_by` `seed:dryrun`, only when the row is still the migration seed, so an operator stop survives a restart). Sandbox mode never takes that path and keeps the switch OFF until the owner approves. Recovery, reconcile and the job loop run in the dry-run demo; they pause when an operator stops the switch. In dry run an operator can stop; turning it back on follows the normal rule (MFA and an active approval row).
- **Environment label (L3).** `NEXT_PUBLIC_UMS_ENV_LABEL` must agree with the mode (offline: Dry run; sandbox: Sandbox) or boot is refused (`label_mode_mismatch`); the footer and page description follow the stored label (L2).
- **Build stability (L4).** `apps/web/next-env.d.ts` and `apps/web/tsconfig.json` are committed in the form `next build` writes and are skipped by prettier and eslint, so a build leaves the tree clean. Root scripts call `corepack pnpm`.

## Boot refuses a terminal that overrides .env.local (F8, D-059, branch feat/config-env-file-guard)

`loadConfigFromProcess()` now refuses to boot (`env_overrides_file`, exit 78) when a `.env.local` exists in the current folder and, for any of `UMS_MODE`, `UMS_PAYPAL_CONNECT`, `UMS_DB`, `UMS_PGLITE_DIR`, `DATABASE_URL`, `UMS_OUTBOUND_APPROVAL_REF`, `UMS_OUTBOUND_SCOPE`, `UMS_OWN_MERCHANT_ID` and `UMS_PUBLIC_ORIGIN`, the process holds a value that differs from the file or that the file does not define. Node's `--env-file-if-exists` and Next never replace a value the process already holds, so such a terminal used to win silently. The refusal names the variable, never a value, and says to run `env -u NAME` or fix the file. A process that holds no value for a name, and a folder with no `.env.local` (the hosted app), pass. Every other name, the secrets included, is never compared. The check runs in offline mode too. The web app, the safety tool and the conformance runner all load through this function.

Reading of the spec, for the reviewer:

- **`order.paid` goes to the buyer, not the seller.** The spec says the seller key subscribes to `order.paid` and `sale.recorded`. The event table (`WEBHOOK_OWNER_EVENTS`) lets a seller subscribe to `sale.recorded` and `refund.completed` only, so P1-04 shows the seller key refused for `order.paid` (`event_type_not_allowed`) and the buyer's client key subscribes to `order.paid` and `mandate.exhausted`. The sink still holds 50 `order.paid` and 50 `sale.recorded`.

- **The 60 offers at $0.10 are seeded with lane B's `extraOffers` helper**, not created over the seller API: a buyer holds each article once, so 50 purchases need 50 articles, and the seller API creates offers for articles the seller already has.
